给编辑器加入 AI 功能时，生成文字往往只是最容易演示的一步。真正进入日常使用后，用户会在等待结果期间继续打字、移动光标、调整段落，还会撤销已经采纳的修改。建议如果只保存一个字符下标，几次编辑后就可能落到错误的位置。

我更愿意先把建议理解成“针对某一份正文提出的一次候选变更”。它不是已经写入文档的内容，也不能因为模型返回成功就自动拥有修改当前正文的权利。

## 发起请求时保留基础快照

快照至少需要文档身份、正文版本、结构化内容和选区描述。只有一段纯文本不足以表达标题、列表、引用和代码块的位置。对富文本编辑器来说，区块标识与编辑器内部位置都很重要：前者方便模型描述目标，后者支持实际事务。

选区也不能只记录选中的几个字。相同文字可能在多个段落出现，可以同时保留所属区块、前后文和精确位置。后续采纳时先确认文档身份一致，再确定当前选区是否仍能对应到原始范围。

## 建议预览与正文分开保存

预览可以通过装饰层、高亮或旁边的建议面板展示。用户在确认前，自动保存和导出应继续使用原来的正文。这样关闭面板、切换文档或取消任务，不需要再构造一系列反向编辑来恢复现场。

把生成文字直接插入正文，再依靠撤销回滚，容易与用户自己的操作交织。用户可能在候选中间继续输入，自动保存也可能把临时内容持久化。区分候选状态与正式正文，能够显著减少这些时间上的歧义。

## 位置变化不一定意味着冲突

用户在目标段落前新增内容时，目标的位置会整体移动，但原文可能没有改变。可以利用编辑器事务的映射机制更新候选范围，再比较当前范围中的原始内容。只要映射明确且文本一致，仍然允许采纳是合理的。

如果用户修改的就是目标文字，或者删除了范围的一部分，就不应继续按旧候选替换。此时展示“原文已变化，请重新生成”比尝试猜测修改意图可靠。跨多个区块的建议还要核验区块顺序，不能仅靠首尾位置判断。

## 一次采纳对应一次编辑事务

采纳一条建议时，可以把删除原范围、插入新内容和恢复合理选区放进同一个事务。采纳全部时，则先统一检查所有候选是否冲突，再按不会破坏后续位置的顺序应用，避免执行到一半才发现后面的目标已经失效。

撤销体验应与用户看到的动作一致。点击一次“接受全部”，通常期待一次撤销就恢复到接受前，而不是连续按很多次才能找回原文。实现时需要理解编辑器历史分组机制，并用真实事务验证，不能只检查页面上的按钮状态。

## 删除和插入也需要目标证明

删除建议没有新文字，更容易被忽略。系统仍然要说明删除什么、为什么删除以及目标是否完整读取。插入建议则要明确位于哪个边界，避免两条建议同时插在相同位置后出现顺序混乱或重复段落。

下面这类结构比一句“优化第二段”更容易校验。证据引用记录在说明中，不必强行混入待插入的正式正文。

```json
{
  "operation": "replace",
  "target": { "kind": "block_range", "first_region_id": "b3" },
  "content_markdown": "修改后的段落",
  "explanation": "保留结论，补足适用条件"
}
```

## 从用户动作验证完整链路

至少应覆盖等待期间在前面插字、修改目标、删除目标、切换文档，以及接受后撤销这几类动作。对于精确选区，还应验证同一个区块里存在重复文字时不会选错范围。

测试不能只断言生成接口返回了建议。需要检查编辑器文档实际发生了什么变化、历史栈能否还原，以及自动保存最终保存的是哪一版。把这些基础行为做稳后，再增加更复杂的生成策略，AI 功能才会成为用户可以放心使用的写作工具。
