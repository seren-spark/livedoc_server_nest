# RAG 可观测性字段

> 合成排障材料，用于验证检索结果是否能回溯到一次具体运行。

## 一次请求需要回答哪些排障问题

用户反馈“这次回答不对”时，通常无法仅凭页面文字确定原因。问题可能发生在资料范围、召回、排序、证据压缩或最终生成环节。排障记录需要把这些阶段串起来，让开发者能够看到系统实际做过什么，而不是根据当前数据库内容猜测历史请求。

同一个问题再次提交可能得到不同的候选和答案。模型配置、文档更新以及查询改写都会影响结果。因而实验记录应以具体的一次执行为单位，保留当时的必要状态；不能把后来手动搜索到的材料认定为先前生成答案时已经使用的证据。

## 核心记录清单

排查 RAG 请求需要记录 trace_id、查询变体、Dense 与 Sparse 候选数、RRF 融合数、重排数、引用的 doc_id、chunk_id、document_version、各阶段耗时、模型版本和索引版本。

这份清单同时覆盖执行路径、规模、来源和时间。只有总耗时无法判断慢在哪一步；只有答案引用无法判断相关材料是否曾经进入候选。记录应允许比较不同实验中的同一个问题，同时注明调用失败和正常空结果，避免将缺失数据默认当成成功。

## 来源链路

片段进入最终上下文之前，可能经过压缩或去除重复内容。报告需要区分检索候选、实际提供给模型的证据以及模型在答案中明确引用的内容。这三个集合可能不同，不能因为某条材料出现在搜索接口返回值中，就宣称模型已基于它完成推理。

引用跳转还应能够找到对应历史原文。若文档随后被编辑，引用所指内容与当前页面不完全一致，需要依靠执行时保存的状态进行解释。诊断信息不应只使用可随时变化的标题，尤其是在多个用户创建同名笔记时。

## 默认内容边界

默认不保存完整 Prompt 与文档正文。运行指标主要用于观察系统行为，而不是复制整份知识库。确实需要核对实际入模材料时，应使用明确授权的评测数据或受控诊断入口，并给出保存范围和保留方式。

日志也应避免打印环境变量、认证头和模型服务返回的完整错误对象。外部错误对象可能嵌入请求参数，直接输出会扩大暴露范围。日常排查通常只需要阶段名称、错误分类和关联编号，然后沿受权限保护的业务入口读取必要详情。

## 延迟分析

观察延迟时要分清首次加载与稳定运行。首次加载本地模型、建立远程连接或者建立缓存都可能产生额外开销。比较两种策略前，先说明是否进行了预热，并保持请求范围、资料版本和硬件资源一致，避免把启动成本误归因为算法质量。

失败请求也应保留耗时，单独展示失败率和已完成请求的延迟分布。不能删除超时样例后只发布漂亮的平均值。如果并发任务争用模型资源，应记录当时的负载条件，便于判断需要优化检索路径还是调整任务调度。

## 复现方式

一份可用报告应包含执行配置、输入数据版本和逐题结果，并能指出哪些资料处于本次允许范围。复跑前核对这些信息，运行结束后再次检查是否发生变化。若环境在实验中漂移，应保留报告用于诊断，同时停止把它用于严格的策略配对比较。
