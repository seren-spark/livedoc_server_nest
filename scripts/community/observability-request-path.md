一个用户说“刚才点生成等了很久”，监控面板上的平均响应时间却看起来正常。原因可能是少数请求在排队，也可能是一次外部调用重试了，或者结果已经生成但提交校验还在等待。只靠一条总耗时日志，很难确定应该改哪里。

可观测性的目的，是让一次用户操作能够被解释。日志、指标和追踪并不是互相替代的三套工具，而是在不同尺度上帮助我们理解同一条执行路径。

## 先给请求建立关联身份

用户操作进入服务时生成请求标识，并把它传到数据库访问、后台任务和外部调用记录中。如果一次操作拆成多个子任务，还应记录父子关系，避免把所有并行调用混成一串没有结构的时间戳。

请求标识不等于用户身份，也不应被用来替代授权。它主要帮助排查与关联，可以在错误提示中提供一个方便沟通的编号，但不能把内部凭证或敏感业务字段直接塞进编号。

## 把等待分成能够行动的阶段

一条文档生成路径可以拆成接入、排队、读取资料、检索、模型调用、结果校验和持久化。每个阶段记录开始、结束、结果和必要的资源用量。这样发现变慢后，才能知道应该增加执行名额、优化查询，还是调查供应商响应。

并行阶段要保留重叠关系。两个任务各耗时三秒，并不意味着用户一定等待六秒；但它们消耗的调用次数与 Token 仍需分别累计。耗时与成本是两个维度，不能简单使用同一种加法解释。

## 重试要同时保留单次与整体视图

外部服务失败后有限重试，可能让最终请求成功，却明显延长等待。外层阶段记录最终结果与总耗时，内层每次尝试记录耗时、失败分类、退避与用量，才能看见成功背后的代价。

```text
根请求
  ├─ 检索：成功
  └─ 模型阶段：成功，总等待较长
       ├─ 第一次：临时服务错误
       ├─ 有限退避
       └─ 第二次：成功
```

如果只保留最后一次成功，会低估供应商的不稳定；如果把第一次失败直接算成整条请求失败，又会误判用户实际结果。两层记录各自表达事实，诊断时再组合分析。

## 指标看趋势，具体请求看细节

指标适合观察请求量、失败率、等待分位数、队列积压和预算消耗。平均值可能掩盖长尾，因此需要结合分位数与样本量判断。一次小样本测试的高分位值，也不能直接当作全站稳定性能。

指标标签要控制种类。把每个请求标识、文章标题或完整错误文本都作为标签，会制造大量不同序列。具体请求的细节应放在日志或追踪中，指标保留有限的阶段、状态和错误类别。

## 记录足够信息，但不复制用户资料

排查模型调用通常可以记录模型名、提示词版本、内容摘要哈希、输入输出用量和工具协议版本，并不需要保存完整用户正文。数据库连接串、访问令牌和供应商原始诊断也不适合直接进入长期日志。

如果确实需要临时检查内容，应使用明确的权限与保留期限。把敏感数据提前从常规日志中排除，比等截图或日志归档扩散后再清理更容易，也不会削弱大多数性能排查能力。

## 建立一条从反馈到证据的排查顺序

拿到用户反馈后，先确认时间范围和请求身份，再看根结果、各阶段耗时和失败分类，最后才深入具体调用。不要一开始就凭经验猜是数据库或模型慢，也不要把所有服务都重启后再试图复现。

修复完成后，用同一条用户路径验证变化，检查耗时之外的状态正确性。一个把错误隐藏起来、快速返回空结果的接口，并不能因为响应时间下降就算优化成功。可观测性真正的价值，是帮助团队用证据决定下一步，而不是只积累更多日志。
