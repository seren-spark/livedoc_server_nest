把一个任务拆给多个 Agent，最容易得到的结果是几段各自流畅的总结。主管看到每个子任务都执行成功，便开始拼接正文。但其中一段可能只找到部分信息，另一段发现两份资料矛盾，这些重要边界如果藏在长段落中，汇总时很容易被遗漏。

工程上的交接需要回答三个问题：已经知道什么，依据是什么，还有什么没有解决。单独一个成功状态或一段摘要，都不足以表达这些信息。

## 执行状态和证据覆盖度分开

子任务成功，通常意味着工具调用和协议交付正常结束，并不意味着用户询问的全部字段都有答案。例如资料明确没有预算金额，研究者准确报告了这个缺口，也是一种有效完成。

可以把覆盖度单独表达为完整、部分、不足或存在冲突。这个状态应由结构化字段推导，而不是让模型随意写一句“已经全部核实”。即使标为完整，也只是当前交付没有报告缺口，不是语义正确性的证明。

## 每条事实绑定实际观察到的证据

交接结构可以保持很小：事实列表、缺失项列表和冲突列表。事实及冲突引用真实的证据标识，下游再同时接收这些标识对应的原始片段，避免只依赖另一个模型的转述。

```json
{
  "findings": [{ "statement": "回滚窗口为发布后24小时", "evidence_ids": ["source-a"] }],
  "missing": ["当前资料未记录审批负责人"],
  "conflicts": []
}
```

服务端可以检查结构、长度以及引用是否确实被当前任务观察并采用。它无法仅凭这些字段证明每句话都受到语义支持，因此仍需要业务评测和必要的人工复核。不要把来源存在等同于结论一定正确。

## 依赖关系决定谁能够看到什么

两个并行研究任务应拥有独立消息和工具状态。只有显式依赖了上游结果的任务，才接收相应交接与证据。同批任务彼此没有依赖时，不应通过全局变量看到对方尚未完成的内容。

最终编辑正文还需要额外谨慎。阅读资料的 Worker 已经读过某段，并不能证明负责修改的 Agent 校验过当前目标位置。生成编辑候选的一方仍应独立读取目标快照，避免继承一份已经失效的位置证明。

## 主管处理缺口，而不是只统计完成数量

收到结构化交接后，主管可以决定继续派发原步骤、在授权范围内补查、向用户澄清，或进入最终汇总。必要步骤不能因为已有两段看起来完整的总结而被跳过。

缺口也不意味着必须继续搜索。如果用户只要求基于当前资料回答，明确说明资料没有记录某项信息，可能已经满足需求。只有存在合理补查路径且预算允许时，继续研究才有价值，否则容易形成重复检索循环。

## 共享预算要给交付留出空间

并行任务不能各自按完整的根预算行动。调度时需要预留后续必要步骤、主管决策和最终提交所需额度，再把当前可用轮数分给同批 Worker。最后一轮应提交已有事实与缺口，而不是继续调用搜索工具。

真实模型可能忽略自然语言提醒，因此可以在请求层明确指定最后一轮的交接工具。结构和证据校验仍然保留，无法按协议交付时就明确失败，不能为了看起来完成而绕过验证或悄悄增加总预算。

## 用业务问题验证协作是否有效

评测应同时覆盖事实查询、来源冲突、信息缺失、条件与例外，以及含中间汇总步骤的依赖计划。不只看有没有最终文本，还要检查关键事实是否引用正确来源、缺失项是否保留，以及是否扩大了资料范围。

多 Agent 往往会增加调用次数、耗时和 Token。简单问题继续直接执行通常更经济。分工真正带来的价值，应体现在证据组织、复杂依赖和可排查性上，而不是通过增加角色数量制造看起来更复杂的流程。
