接口测试里最容易获得的绿色结果，是发送请求后断言返回成功。但保存接口返回了新版本号，并不一定表示正文已经持久化；公开列表返回了文章，也不一定表示未发布草稿没有泄露。协议成功只是需要检查的一部分。

设计测试时，可以先从用户能够观察到的业务结果出发，再决定哪些断言应该放在单元、接口或真实依赖测试中。不同层次提供不同证据，不能用其中一个代替全部。

## 先明确一次操作改变什么

例如保存草稿，应当改变当前作者的草稿内容和版本，而不改变已经发布的公开正文。发布操作则形成新的公开快照，并按选择创建索引任务。把这些不变量写清楚，测试才知道成功之后还需要读取哪里。

返回值可以检查字段格式与版本信息，重新查询验证对外可见状态。关键持久化能力还可以通过重建服务实例验证，避免测试恰好读取了同一进程里尚未真正保存的对象。

## 权限测试需要身份矩阵

准备作者、同空间其他用户、不同空间用户和未登录访问者，分别检查读取、修改、发布和公开访问。不要仅凭某个用户能正常保存，就推断所有用户隔离已经正确。

权限还可能在请求执行期间变化。对于长时间检索或生成，开始时有权读取，不代表最终输出时仍然有权。可以让外部调用暂时等待，中途撤销来源，再验证迟到结果不会被提交给用户。

## 版本冲突属于正常业务状态

同一篇草稿被两个标签页打开，旧标签页提交时应得到清晰的版本冲突，不能覆盖较新的内容。测试需要分别保存两个不同版本，再确认最终正文对应哪次成功提交。

```text
读取版本 1
  ├─ 请求 A：保存新正文 → 成功，版本 2
  └─ 请求 B：仍基于版本 1 → 冲突

重新读取 → 应为请求 A 的正文
公开读取 → 仍为上次发布快照
```

这类检查比单独断言一个冲突状态码更完整。状态码说明请求被拒绝，重新读取才能证明旧请求确实没有部分写入其他字段。

## 对失败路径检查有没有遗留状态

事务中间失败时，可能已经创建了公开快照，却没有更新文章状态；也可能写入了任务，但对应文档没有提交。可以在可控制的位置制造异常，检查所有相关业务状态是否一起回滚。

不要只把整个仓储替换成返回错误的函数。那样无法说明事务内部已经发生部分操作时会怎样。测试应选择真正需要验证的边界，再决定用实际数据库事务还是具有明确语义的存储替身。

## 幂等与并发不能只顺序测试

重复创建评论时，顺序执行两次通常只能验证查重分支。两个请求同时到达，才能检验唯一约束是否真正发挥作用。最终检查记录数量、返回结果和是否出现未处理的冲突异常。

点赞、收藏和任务入队也有相似问题。用户状态、聚合统计和列表应来自一致的关系记录，不能只验证某个接口把计数加了一，而忽略重复请求导致的多次累加。

## 区分受控测试与真实依赖验证

受控模型和内存存储适合稳定验证协议、调度与错误处理。真实数据库测试能够验证持久化和 SQL 事务，真实检索与模型测试则观察外部系统行为。这些结果应分别记录，不能因为受控测试全部通过就声称生产链路已经验收。

真实测试也需要限定数据范围。优先创建具有独立标识的合成资料，不读取无关私人内容；是否保留或清理数据，应与测试目的保持一致，避免验收脚本误删用户已经编辑的文章。

## 让失败报告能够指导下一步

一次失败至少说明是哪条用户路径、使用了什么身份、预期哪个不变量，以及实际观察到什么。接口错误、检索没有证据和模型回答遗漏，是不同问题，不能全部归类成“生成失败”。

测试的价值不是让一张结果表尽可能绿，而是为系统当前能力提供可信证据。把状态码、业务结果和持久化事实连起来，才更容易发现那些表面成功、实际损坏数据的错误。
