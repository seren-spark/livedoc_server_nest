用户点击提交评论后没有立即看到响应，于是又点了一次。也可能是客户端自动重试，或者网关在连接中断后重新转发了请求。前端把按钮禁用可以减少误操作，却不能成为服务端避免重复创建的唯一保证。

幂等性讨论的核心不是“同一个接口只能调用一次”，而是相同的业务意图被重复送达时，系统应当产生怎样可预测的结果。

## 为一次业务意图建立身份

客户端可以在用户真正发起一次创建动作时生成请求标识，并在网络重试期间继续使用它。用户修改内容后重新提交，则属于另一次意图，应该使用新的标识。

标识还需要明确作用域。同一个字符串在不同用户、空间或接口中出现，不一定代表同一件事。常见设计会将用户、操作类型和请求标识组成唯一约束，避免不同业务之间互相占用身份。

## 同一个键不能承载不同内容

如果第二次请求复用了相同标识，却提交了不同正文，直接返回第一次结果会让调用方误以为新内容已保存。更清晰的做法是保存规范化请求摘要，只有摘要一致才允许回放。

规范化也需要边界。可以对确定无意义的格式差异采用一致序列化，但不能随意删除有业务意义的字段。比如评论内容中的空白、文件版本或目标文章，都可能影响用户实际想提交的结果。

## 唯一约束处理真正的并发

“先查是否存在，再创建”在两个请求同时执行时仍然可能都查不到。数据库唯一约束应当作为最终保证，让只有一个请求成功占有这次业务身份。

```text
用户 + 操作类型 + 请求标识 → 唯一业务请求
                        → 规范化请求摘要
                        → 处理中 / 已完成 / 可重试失败
                        → 已提交的业务结果
```

成功插入业务记录和保存可回放结果，最好处于同一个事务边界内。这样不会出现评论已经创建，但幂等记录仍显示不存在，导致下次请求再创建一条的情况。

## 处理中和已完成要区别对待

第二个请求到达时，第一个可能还没有完成。可以返回明确的处理中状态，或者在有限时间内等待已有结果，不能再启动一套相同的长任务。选择哪种方式取决于接口的等待成本与交互需求。

失败也不是一个统一状态。业务校验失败通常应稳定返回同样的错误；网络超时则需要先确认业务是否已经提交，不能因为客户端没收到响应就推断服务端没有执行。对于外部副作用，还需要目标服务提供相应幂等能力或可核对的业务标识。

## 后台任务的幂等边界有所不同

同一文档版本重复请求索引，可以合并到同一个有效任务，但文档内容发生变化后就应形成新的任务身份。否则新版本会被误判为已经处理，永远得不到最新索引。

任务重试还要避免重复激活或重复发送通知。完成提交时核验当前版本与执行权，比单纯保存一个“已经开始过”的布尔值更可靠。执行过与成功产生当前业务结果，并不是同一件事。

## 回放结果也需要当前授权

幂等记录中可能保存正文、资源标识或生成结果。再次请求时除了核对身份，还应检查当前用户是否仍能访问这些资料。不能让历史结果绕过撤权或资源删除后的正常限制。

保存期限同样要与业务需求一致。短期网络重试与长期订单创建的要求不同，不能机械使用一个统一过期时间。记录过期后是否允许重建，应通过业务唯一键和当前状态继续约束。

## 验证不能只有顺序重复调用

测试至少包括同时发起两个相同请求、同键不同内容、首次响应丢失后重试，以及用户身份不同但标识相同。检查的重点是最终业务记录数量、结果是否一致和错误是否可理解，而不只是两次都返回成功。

幂等设计做得好，调用方就能在不确定的网络环境里安全重试。它让系统承认消息可能重复到达，并把重复这件事转化为正常可处理的状态，而不是依赖每个客户端都永远只点击一次。
