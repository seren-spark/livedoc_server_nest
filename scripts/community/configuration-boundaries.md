同一份代码在测试里正常，重启开发服务后数据却不见了；或者本地调试时意外连接了另一套数据库。这些问题经常来自配置来源不清，以及测试替身和真实运行模式之间缺少明确边界。

配置管理不必从复杂平台开始。先让服务能够明确说明自己读取哪份配置、正在使用什么存储，以及缺少必要条件时怎样失败，就能减少许多不确定性。

## 配置来源要有明确顺序

环境变量、项目配置文件和默认值之间，应有稳定且可解释的优先级。脚本从不同目录执行时，也应读取预期项目的配置，而不是依赖当前终端碰巧位于哪个路径。

可以由配置模块统一解析项目根目录，并记录实际配置文件位置。不要让数据库脚本、后台 Worker 和 API 服务分别实现略有不同的查找逻辑，否则它们可能看似使用同一环境，实际连接不同资源。

## 真实运行与测试替身显式区分

内存数据库、哈希向量和固定模型响应，在隔离测试中非常有价值，能够稳定验证协议与状态变化。但真实运行模式下缺少数据库或模型凭证时，不应悄悄替换为这些实现。

隐式降级会让服务看起来成功启动，用户也能暂时保存内容，直到重启以后才发现数据从未持久化。更清晰的做法是在启动时拒绝不完整配置，并告诉维护者缺少哪种能力，而不是打印敏感参数。

## 验证组合，而不只验证单个值

某个配置字段存在，并不表示整套组合可用。例如选择真实向量库却没有地址，或生产模式仍允许无身份开发登录，都属于组合约束。校验可以集中在启动入口，让 API 与 Worker 遵守同一套规则。

```text
运行模式：真实 / 隔离测试
元数据：持久化存储及必要连接
检索：向量、稀疏召回、重排的兼容组合
模型：接口、模型名与可选能力
访问：监听地址、跨域来源与认证模式
```

不需要把所有可选能力都变成启动必需条件。某个功能确实允许关闭时，应显式表达为关闭，而不是用一个错误地址假装已经配置，再等用户调用时才暴露问题。

## 配置诊断避免暴露秘密

诊断可以展示当前供应商类型、资源名称、连接是否可达以及缺失字段名。数据库密码、访问令牌和完整认证头不应出现在日志、截图或提交记录里。需要定位数据库时，可以只展示主机、端口与库名。

外部服务报错也要经过分类。保留足够的状态码、请求身份和重试信息，但不要无差别转发供应商原始响应，因为其中可能包含内部细节或用户输入片段。

## 脚本也属于运行入口

迁移、数据导入、评测和后台任务脚本，同样需要遵守配置边界。一个合成题评测如果本来只想测试模型，就应在构建应用前显式注入隔离存储，避免导入模块时先连接真实数据库。

真实数据导入则相反：应确认写入的是应用实际使用的持久化来源，不能只在内存中生成几条漂亮结果就宣称页面已经充实。只读校验与实际写入也应通过明确参数区分，方便维护者理解命令的影响。

## 配置变更需要可核对的版本

排查故障时，代码版本与配置摘要都重要。可以记录不含密钥的配置指纹，以及模型、索引代次或处理协议版本，帮助判断两个结果是否来自相同环境。

不要依赖运行人员记得曾经在终端里设置过什么变量。长期需要的值应回到明确的配置来源，临时测试变量则限定在单次进程，避免影响后面启动的真实服务。

## 用启动与重启验证边界

检查缺配置时是否明确失败、真实模式是否拒绝测试替身，以及数据在服务重启后是否仍能读取。对于多个进程组成的系统，还要确认 API 与 Worker 使用相同的数据库和兼容索引设置。

清楚的配置边界不会消除所有环境差异，但能让差异尽早暴露，并让维护者知道当前服务究竟具备哪些真实能力。它减少的是那些看起来一切正常，却在真正使用时才发现运行在另一种模式中的意外。
