一个对象上同时存在 status、data、error、pending 和几个可选版本号时，调用方经常不知道应该先检查哪个字段。类型允许的组合很多，真正合法的业务状态却只有少数几种，剩下的判断便散落在每个组件和服务里。

TypeScript 可以帮助表达这些约束，但前提是类型围绕业务事实设计，而不是把接口返回的任意字段原样堆进一个大对象。

## 把互斥状态写成不同分支

如果加载结果只能是等待、成功或失败，就可以使用带区分字段的联合类型。成功分支必定有结果，失败分支必定有错误，不需要每个调用方再猜测 data 和 error 是否同时存在。

```ts
type LoadState<T> =
  | { kind: 'idle' }
  | { kind: 'loading'; requestId: string }
  | { kind: 'ready'; value: T }
  | { kind: 'failed'; message: string };
```

根据 kind 判断后，编译器能够收窄字段范围。这样的好处不是少写几次问号，而是把“成功时应该有什么”变成所有调用方共同遵守的规则。

## 不同维度不要强行挤进一个状态

文章是否公开、索引是否就绪和草稿是否有未发布修改，是不同维度。一个文章可以已经公开，同时新索引仍在处理中，也可以有一份尚未发布的新草稿。把这些组合都塞进单一状态枚举，会很快出现难以理解的名称。

可以分别表达发布状态、索引状态和版本关系，再在确有必要时提供派生判断。类似地，Agent 子任务执行成功与证据覆盖完整也应分开，避免把“正常结束但缺少资料”误判成程序故障。

## 内部类型与外部输入有边界

网络请求、数据库历史值和外部模型输出，都不会因为代码里写了一个类型断言就自动变得可靠。输入应先视为 unknown，在边界进行运行时校验，再转为内部使用的类型。

校验内容包括字段、允许值、长度以及必要的业务约束。结构合法也不等于业务合法，例如引用字段是字符串，并不能证明它属于当前用户实际读取过的资料，仍需进一步核对来源。

## 类型应当帮助维护状态转换

从草稿到发布，需要形成公开快照并记录发布版本；撤回则改变对外可见资格。可以把这些转换集中在拥有业务状态的服务里，而不是允许任意调用方直接修改 status。

如果转换涉及数据库并发，类型不能替代条件更新、事务与唯一约束。编译期知道需要版本号，运行时仍然必须检查版本是否匹配。两者负责不同层面的正确性，配合使用才有意义。

## 序列化时注意时间和集合

Date、Map、Set 等对象跨过 JSON 边界后，不再保持原来的运行时形式。接口类型如果继续声称返回 Date，前端就可能在字符串上调用日期方法。可以明确传输类型与内部类型，并在入口恢复需要的结构。

可选字段和 null 也应约定清楚。缺少字段可能表示未请求这项信息，null 可能表示明确没有值，空字符串则是另一种内容。没有必要让每个字段都拥有三种空状态，除非业务确实需要区分。

## 避免为类型抽象增加额外绕路

联合类型并不要求引入庞大的状态机库。许多场景用几个明确分支和集中转换函数就足够。只有状态、事件和转换关系已经复杂到难以维护时，再考虑专门机制更合适。

同样，不必把所有对象都拆成许多只使用一次的泛型。评估一个类型设计，可以看读者是否更容易知道当前状态允许做什么，而不是看它用了多少高级语法。

## 用真实边界验证设计

可以从保存冲突、任务取消、接口缺字段和历史数据迁移等场景检查类型是否准确。若调用方频繁使用强制断言绕过限制，往往说明边界没有验证清楚，或者类型没有表达实际业务。

好的类型设计会让合法路径更自然，让不合法组合更难出现。它应该降低日常阅读和修改的负担，同时与运行时检查共同提供证据，而不是制造一种“编译通过，所以业务一定正确”的错觉。
