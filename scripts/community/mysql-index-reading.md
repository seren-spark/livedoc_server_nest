文章系统里一条常见查询是：查看某位作者已发布的文章，按最近更新时间排序，每页读取少量记录。表结构里可能已经有作者、状态、时间等多个单列索引，但数据库仍然扫描很多数据或额外排序。这时需要回到查询本身，而不是继续盲目添加索引。

索引是有维护成本的数据结构。一个合适的联合索引，应当服务于已经存在且值得优化的查询模式，而不是试图为所有想象中的筛选组合预先准备答案。

## 把过滤和排序完整写出来

先列出等值条件、范围条件、排序字段和返回字段。多租户系统还要考虑空间或用户边界，不能只在示例里写作者 ID，实际查询却额外增加另一个高影响过滤条件。

```sql
SELECT article_id, updated_at
FROM article_drafts
WHERE space_id = ? AND owner_id = ? AND state = 'published'
ORDER BY updated_at DESC, article_id DESC
LIMIT 20;
```

针对这类查询，可以从空间、作者、状态、排序字段组成的索引开始分析。这里先观察窄字段查询，是为了看清过滤和排序的成本；列表需要的大段 JSON 正文不应无条件放进覆盖索引。

## 联合索引不是字段集合

索引列的顺序会影响可用的查找和排序方式。等值过滤缩小范围后，后续排序列才有机会直接提供所需顺序。把几个字段都放进一个索引，并不意味着它能同样高效地支持任意字段组合。

例如，不筛选状态的“作者全部文章”查询，和固定状态的查询并不完全相同。如果状态列位于时间列之前，跨多个状态取全局时间顺序，可能仍然需要额外排序。应分别查看真实执行计划，而不是只确认查询出现了某个索引名称。

## 用执行计划提出问题

执行计划可以帮助观察访问方式、使用索引、估计扫描量和是否出现额外排序。具备实际执行分析能力的环境，还可以比较估计与真实行数，发现数据分布或统计信息带来的误判。

但工具输出不应成为孤立的评分表。看到排序并不一定意味着必须立即优化，少量结果排序可能成本很低；看到使用索引也不代表足够快，宽范围扫描和回表仍可能占据主要耗时。

## 返回字段也会影响成本

列表如果只显示标题、摘要和作者，不必把完整正文和编辑器 JSON 一起读取。大字段增加传输、内存与解析负担，有时远比一次轻量排序更值得先处理。

覆盖索引可以减少部分查询的回表，但不能为了让所有字段都覆盖，就把长摘要或大型 JSON 堆进索引。索引越宽，缓存利用率和写入维护成本也可能变差，需要按实际访问频率和记录大小判断。

## 深分页是另一类问题

即使排序可用索引，较大的 OFFSET 仍可能需要读取并跳过许多记录。公共时间线可以考虑基于稳定排序键的游标分页，后台管理则可能继续使用页码，并限制过深的跳转范围。

不要把索引优化和分页语义混在一起。换索引未必能消除深分页成本，换游标也不能替代权限过滤或正确排序。每项改动都应明确它减少了哪个阶段的工作。

## 验证读收益与写成本

准备与实际分布相近的数据，分别执行常见查询和边界查询，再观察耗时、扫描量与写入行为。单一作者只有几篇文章时的结果，不能直接推断拥有大量历史内容的作者也有相同表现。

新增索引后还应检查发布、保存和批量导入的影响。没有被使用的重复索引可以在确认依赖后清理，但不要只凭索引名字相似就删除。最终目标是用更少的资源完成有价值的查询，而不是让表上出现尽可能多的索引。
