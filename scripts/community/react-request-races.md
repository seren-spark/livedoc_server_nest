搜索框最容易让人误判的故障，是输入和页面结果看起来都没有报错，却属于不同的时刻。用户先输入“事务”，紧接着补成“事务隔离”，第二个请求先返回，页面显示正确内容；几百毫秒后第一个请求结束，又把列表改回去了。接口没有失败，真正出问题的是客户端接受结果的条件。

下面用一个普通文章搜索页面说明处理方法。例子中的延迟只是为了复现时序，不代表某个真实接口的性能数据。

## 先把一次查询的身份定义清楚

查询身份不只有输入框文字。筛选标签、当前页、排序方式和登录用户，都可能影响结果。如果只在关键词改变时清空状态，切换分类后仍可能收到旧分类的结果。实践中可以把这些条件整理成一个稳定的查询键，让请求、缓存和界面状态使用同一套定义。

显示列表之前也要决定交互策略：用户开始新查询时，是暂时保留上一页并标记更新中，还是清空旧数据显示骨架屏？两种方式都可以，但标题、页码与列表必须表达同一个状态，不能一边显示新条件，一边让旧结果看起来已经更新完成。

## 取消请求与拒绝旧响应各自负责什么

取消请求可以减少不必要的等待和传输，却不能证明服务器没有继续处理，也不保证后续的解析或缓存读取一定停止。因此需要两层处理：离开当前查询时触发取消，在真正提交状态时再确认这个结果仍属于当前查询。

一种简单实现是在每次副作用中维护活动标识，清理时将它失效。活动标识属于这一次副作用，不能放在所有组件共享的全局变量里，否则多个搜索页面会互相取消。如果请求来自一个不能取消的接口，活动检查仍然有效。

```tsx
useEffect(() => {
  const controller = new AbortController();
  let active = true;
  setLoading(true);

  searchArticles(query, controller.signal)
    .then(result => {
      if (active) setArticles(result.items);
    })
    .catch(error => {
      if (active && error.name !== 'AbortError') setError('搜索失败');
    })
    .finally(() => {
      if (active) setLoading(false);
    });

  return () => { active = false; controller.abort(); };
}, [query]);
```

## 加载状态也有归属

常见遗漏出现在 finally：旧请求虽然不再更新列表，却仍然把 loading 设置为 false。此时新请求还没结束，页面的加载提示已经消失。错误信息也一样，旧查询失败不能覆盖新查询的成功结果。这些写入都应使用相同的活动检查。

如果一次查询包含多个并行请求，例如列表和总数，可以分别管理完成状态，也可以在全部完成后统一提交。关键是先明确页面是否允许部分展示，避免一个请求失败导致另一个已经成功的区域被无意义地清空。

## 防抖解决频率，竞态处理解决正确性

防抖只是在用户停止输入一小段时间后再发起请求，它减少请求数量，但无法保证请求按顺序返回。用户输入速度变慢、网络出现抖动，仍然可能存在两个同时进行的请求。因此即使加了防抖，也应保留取消和提交检查。

此外，立即反馈和实际查询可以分开。输入框应及时反映按键，列表使用防抖后的查询条件。不要让输入值本身等待定时器更新，否则中文输入、清空操作和键盘交互都容易变得不自然。

## 文档切换比搜索更需要谨慎

同样的模式也会出现在编辑器切换文档时。A 文档的读取比 B 文档慢，如果响应回来就直接设置编辑内容，用户可能看到标题已经是 B，正文却被 A 覆盖。这里的查询身份应包括文档 ID 和版本，保存请求还需要独立的版本校验，不能只依赖界面没有切走。

对于保存、删除等有业务副作用的操作，取消网络等待也不等于撤销已经完成的服务器修改。前端应重新查询当前业务状态，必要时用请求标识实现幂等，不能简单把所有异步操作都理解成可随意丢弃的搜索结果。

## 用确定的时序验证

测试时不要依赖“网络通常会慢一点”。可以人为控制两个 Promise 的完成顺序：先启动 A，再启动 B，让 B 成功后才释放 A，检查列表始终保留 B。再分别验证 A 失败、组件卸载和 B 尚未完成时 A 的 finally 执行。

排查记录也应包含查询键和是否接受响应，而不只记录耗时。能看到某次旧结果被正常丢弃，说明保护正在工作。最终目标是让输入条件、加载提示、错误提示和可见内容始终属于同一个有效查询，而不是让所有请求都按理想顺序结束。
