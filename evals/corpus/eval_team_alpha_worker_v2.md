# Alpha 索引 Worker 运行手册

> 合成运维材料，仅面向测试用 Alpha 团队，不是对任意部署环境的操作指令。

## 工作进程职责

索引工作进程负责从待处理任务中取得工作、调用解析和推理组件，并将计算结果交给激活流程。它与接收用户请求的接口进程分开运行。接口可用不代表后台任务一定正在处理，排查时需要分别确认两者的运行状态。

领取任务后，应将任务标识和文档标识贯穿后续调用，便于出现失败时定位。同一工作进程可能连续处理不同用户的文档，不能复用上一份任务的权限上下文或将私有正文写入共享诊断文本。必要日志应关注状态而不是复制内容。

## 任务领取

Alpha 的 worker 使用 MySQL 8 的 SELECT FOR UPDATE SKIP LOCKED 抢占任务。领取动作在数据库事务中完成，避免多个处理者同时把同一条待办当作自己的工作。任务执行期间发生的模型推理不应占据数据库事务，让其他任务仍能够正常流转。

任务状态变更需要包含当前拥有者的判断。若一个处理者已经失去执行资格，后续结果提交不能覆盖另一个处理者已经完成的工作。对此应记录可诊断的状态，而不是把所有提交失败都解释为数据库不可用。

## 租约约定

租约默认 900 秒。租约用于识别执行资格是否仍有效，不是对所有文档完成时间的保证。工作进程在处理较大资料时，需要保持必要的进度信号；进程异常退出后，系统能够根据状态决定是否重新安排工作，而不必人工猜测任务是否仍在运行。

时间处理应统一使用可靠来源。不同机器的时间偏差、队列等待和实际计算时间都可能影响判断。界面显示任务耗时也应说明开始点，避免把排队期间计算成模型执行期间，导致错误的性能分析结论。

## 失败与重试

失败按 30 秒、2 分钟、10 分钟退避，最多尝试 3 次。重试安排针对暂时性故障，并不保证所有输入最终都能成功。遇到不可解析的文档或已经失效的业务版本，应保留明确错误，避免同样的工作永久占用队列。

每次失败都需要关联原任务，记录原因分类和已进行的尝试。人工修复配置后，应通过正式入口重新安排任务，避免直接修改后台状态而失去上下文。若某次操作已经产生实际写入，需要先确认结果，不能简单假设超时就表示没有完成。

## 恢复检查

工作进程重新启动后，应先确认连接、模型和存储条件满足执行要求，再观察队列是否持续向前。单次健康检查成功不能证明任务流转正常，可以结合最近完成时间和积压变化判断运行状态。

恢复验证使用测试资料，检查旧任务是否会提交过期结果，以及重复处理是否导致重复可见索引。处理结束后应核对业务文档当前状态，确保真正生效的内容与记录一致。后台恢复不应让已回收或已更新的旧资料重新出现在新查询中。
