# 文档 Agent 与个人知识管理

前端入口：编辑器「AI 助手」或 Ctrl/Cmd + Shift + K；个人知识库侧栏提供分类、模板和回收站。

可恢复的 LangGraph 工作流、MySQL 迁移及启用方法见 [可恢复文档 Agent](./agent-graph.md)。以下旧流式入口仍保持兼容。

## 使用

- Ask 读取资料和回答，不提供正文修改；Plan 生成可调整计划，点击「按此计划执行」后才执行。
- 计划卡的「编辑计划」可手动修改目标、章节、写作要求与步骤，支持增删、排序和步骤类型。保存只更新当前计划；执行时发送保存后的计划及最新编辑器快照，用户确认版本优先于原始计划。
- 侧栏左边缘可拖动调宽，也可聚焦分隔条使用左右方向键；双击恢复默认宽度。宽度保存在当前浏览器，手机端保持全宽。
- 长文生成按内容选择表格、短段落、列表与重点。对比与指标汇总优先用 GFM 表格，`**术语**` 加粗，`==关键结论==` 高亮；纯文本或用户指定格式优先。侧栏预览、采纳、新草稿保存和重开均支持表格与高亮。
- Agent 可直接回答普通问题。输出位置只在用户要求写作或编辑时生效，不会把每轮提问都强制转换成正文修改；与原文相同的替换会被拒绝。
- Agent 发送前选择修改当前文档或新建独立文稿。修改通过正文标记和侧栏前后对比逐项采纳；全部接受为一次撤销操作。
- 正文、选区及光标上下文来自发送时的快照。后续手动编辑只让受影响建议冲突；切换文档取消任务。
- PDF/DOCX 使用既有解析 Worker，解析完成后作为资料，不自动入库。TXT/Markdown 按 UTF-8 读取，单文件 2 MiB，最多 10 份参考资料。
- 知识文档可按名称或内容搜索后选入资料。未选择知识库范围时不会强制检索公开知识库。
- 知识库检索结果包含原文文档标识，Agent 可使用 `read_knowledge_document` 分页追读本任务已发现的文档；每次追读重新校验权限和版本，不能凭任意文档 ID 扩大读取范围。
- 超大表格、列表和代码块支持块内分页。工具返回 `region_id`、`next_content_offset` 与 `partial`，连续片段完整覆盖后才允许将整块计为已读或提交整块修改，不能以末页代替全文。
- 蓝色侧栏保留紧凑的输入框、模式与输出位置。点击书本图标在浮层中选择模板；资料和更多设置按需展开。
- 当前文档的模板浮层说明「按模板重组」，选择表示明确采用模板结构；具体用户需求和选区范围仍优先。新建文稿默认采用所选模板。
- 独立文稿采纳后保存为私有、未索引草稿，留在当前页面并提供编辑链接和 Markdown 下载。下载和保存保留所引用资料的来源。
- 引用来源只展示最终回答、文稿或修改建议实际采用的资料；其他读取记录另列。分页读取使用独立片段标识，保留当时的原文、版本与位置。回答中的引用编号可点击查看证据片段，再打开原文定位；版本或当前快照已变更时不自动定位到旧位置。
- 联网搜索摘要、逐条搜索片段及工具返回的链接按实际来源标示，不把多来源汇总登记成每个网页的原文。
- 个人分类最多三级，列表精确匹配直属分类；标签继续独立保留。删除分类默认把文档移到未分类，可选择一起回收。
- 分类合并是事务操作。恢复合并来源只恢复已清空的分类，不撤销已经迁移的文档。
- 回收文档保留正文和附件，普通检索、引用、资产及模型资料读取不能访问。恢复必要祖先链，按删除批次恢复，避免复活先前单独回收的内容。彻底删除才清理向量、附件、导入源、记忆及索引快照。

## 启用与迁移

保持现有模型、MySQL、Qdrant、解析 Worker 配置。先备份数据库，再在 NestJS 项目运行：

```powershell
npm install
npm run db:migrate
npm run build
```

当前 schema 版本为 `2026101901_agent_user_settings`，在工作台表及文档分类／回收字段的基础上增加个人能力配置表，不自动回填标签，也不自动清空回收站。

分类回填可使用知识库「导入旧标签目录」（仅当前用户），或执行全用户脚本：

```powershell
node --loader ts-node/esm scripts/backfill-categories.ts
```

回填按第一个非空标签创建一级分类，保留标签，跳过已分配分类、已回收文档和文章 projection，重复执行不覆盖人工归属。`全部文档`、`未分类` 为虚拟入口，不回填成实体分类。

软删除上线后，回退服务也必须保留删除状态的读取限制。关闭分类界面开关不清理或转换回收数据。

## 配置

```dotenv
DOCUMENT_AGENT_ENABLED=true
WORKSPACE_ENABLED=true
MCP_ENABLED=false
AGENT_WEB_SEARCH_URL=
AGENT_WEB_SEARCH_MODEL=
AGENT_MAX_TOOL_CALLS=24
AGENT_TIMEOUT_SECONDS=300
AGENT_MAX_OUTPUT_TOKENS=4096
AGENT_THINKING_SUPPORTED=false
AGENT_THINKING_ON_BODY={}
AGENT_THINKING_OFF_BODY={}
AGENT_CLASSIFIER_MODEL=
AGENT_PLAN_MODEL=
AGENT_CRITIC_MODEL=
```

联网检索可复用现有阿里云模型密钥：显式配置 `AGENT_WEB_SEARCH_URL` 为所在地域的原生 DashScope 多模态接口，例如 `https://dashscope.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation`。`AGENT_WEB_SEARCH_MODEL` 留空时使用主模型；部署前应验证该模型和端点支持联网检索及来源返回。工具 `search_web` 强制检索，引用只从接口返回的 `search_results` 建立，缺少来源时报错。`MCP_ENABLED=true` 可额外启用受控网页读取；原生搜索不依赖 Tavily 密钥或 MCP。每轮只有打开「联网检索」才加载和允许执行这些工具。协议说明见 [阿里云联网搜索文档](https://help.aliyun.com/zh/model-studio/web-search/)。

深度思考开启时主模型使用 `tool_choice=auto` 兼容思考与工具调用；普通文字不会直接写入编辑器，必要时通过一次关闭思考的结构化提交补齐终态。工具消息保留调用标识，服务端仅在本次工具对话内临时保留接口要求的推理字段，不写入会话记忆、审计或页面。分类、规划与自检仍使用各自的非思考配置。实际运行验证可执行 `node scripts/verify-agent-features.mjs`（使用本机常驻 API 和演示账号），覆盖思考、思考加联网、关闭联网三个场景。

辅助模型留空时复用主模型，需要支持对应 JSON／工具调用能力。`LLM_CONTEXT_WINDOW` 和 `TOKENIZER_ENCODING` 沿用现有预算配置；调整输出上限时同时核对模型窗口。长文分页读取，工具历史超出预算时压缩并保留引用和分页标识；仍超限则明确要求缩小范围，不把部分阅读称作全文结论。

深度思考只在已声明支持、正确配置请求参数时启用。例如支持 `enable_thinking` 的兼容服务可配置：

```dotenv
AGENT_THINKING_SUPPORTED=true
AGENT_THINKING_ON_BODY={"enable_thinking":true}
AGENT_THINKING_OFF_BODY={"enable_thinking":false}
```

开关作用于主模型；分类、规划、自检默认关闭思考。原始推理字段不进入前端或审计。

## MCP

启用 `MCP_ENABLED=true` 会注册本地受控 Fetch 服务，开发使用 TypeScript 脚本，生产使用构建后的 `dist/ai/mcp-fetch-server.js`。公网 DNS 结果及每次重定向均校验，连接使用校验过的地址；拒绝私网、回环、保留地址和携带用户密码的 URL。最多五次重定向，响应最多 2 MiB，只读取文字网页。

`MCP_SERVERS` 为 JSON 配置。Tavily 示例使用官方仓库当前声明的固定版本，部署时应核对安装来源：[官方 package.json](https://github.com/tavily-ai/tavily-mcp/blob/main/package.json)。

```dotenv
TAVILY_API_KEY=your-key
MCP_SERVERS={"tavily":{"enabled":true,"transport":"stdio","command":"npx","args":["-y","tavily-mcp@0.2.23"],"env":{"TAVILY_API_KEY":"${TAVILY_API_KEY}"},"tools_include":["tavily_search","tavily_extract"]}}
```

stdio 子进程只继承 SDK 的基本运行环境及明确配置的变量，不自动继承数据库、模型密钥。远程服务支持 `transport=streamable_http`、`url`、`headers`，URL 和请求头也支持 `${VARIABLE}` 替换。

只注册白名单工具，不依据第三方声明自动授予写权限。模型工具名包含服务器前缀，必要时规范化并加摘要，满足模型名称限制。发现失败清除该服务的部分注册，其他站内功能继续工作。前端联网默认关闭。

## 状态、审计和限制

`POST /ai/agent` 使用 SSE，返回路由、计划、步骤、工具、自检、候选和终态；增量只展示在侧栏。完整候选经过模式、区域、引用、Markdown 和编辑器节点校验后才可采纳。

- 同用户同时一个执行任务，每分钟最多十次启动；单 API 默认最多六个执行任务，等待用户采纳不占执行名额。
- 计划最多五步，读取／检索步骤最多并发三个；每步最多四轮模型／工具执行循环，全任务默认二十四轮。每个后续必要步骤预留调度、一次读取和交接，另保留最终汇总及一次主管协议修复。自定义较低预算时，规划工具同步降低允许步数；超预算的确认计划在执行前拒绝，不静默提高额度。模型请求、工具执行、Token 分开统计；分类、主管、压缩、自检、Wiki 覆盖判断和内置联网搜索共享累计预算。默认最多 120000 Token、30 次模型请求，研究阶段为最终交付预留 8192 Token 和两次请求。
- 模型调用在发出前同步预留输入估算与最大输出，并发请求不能重复使用同一额度。成功后按供应商用量结算；失败、取消或缺少用量时保留估算扣账，通过 `charged_tokens`、`reserved_tokens`、`estimated_requests` 区别于供应商实际统计。估算额度用于限制任务规模，不等于精确账单。
- 自检及工具修复各最多一次。自检服务不可用时显示未完成；已明确判为有问题的候选若修复失败，则终止交付，不放行原候选。不跳过确定性校验，不重放写操作。
- 新文稿使用固定 ID，保存结果不确定时先查已有文档，避免重复创建。
- 反馈按任务串行合并，避免全部采纳时丢失其中一项；已处理候选不反向改写状态。
- 模板、分类只覆盖个人私有知识文档；文章草稿和团队／公开文档沿用原保存与管理入口。
- 首版为单 API 实例，限流与执行名额为进程内控制。审计正常使用 MySQL，工具审计故障记录日志，不重放工具。
- `GET /ai/agent/:id` 和 `/ai/tool-audits?run_id=...` 仅返回当前用户审计元数据；GET 不包含候选和来源正文，资料失效后仍可查询任务及后台沉淀状态。运行表的 `payload.delivery` 保存通过校验的完整候选、已采用引用、选区描述及覆盖信息，不保存完整编辑器快照。候选仅由恢复接口返回，返回前重新验证目标和来源权限、版本及 Wiki 证明；失效返回 403／404／409，不返回正文片段。
- `POST /ai/agent/:id/restore` 接收 `{editor_json}`；正文完全相同时沿用生成时位置。部分采纳或无关正文变化后，服务端根据生成时保存的块哈希重新定位剩余目标，支持目标文档已保存的新版本；目标变化或位置不唯一时要求重新生成。只保存块哈希，不保存完整编辑器正文。资料来源的权限、版本及 Wiki 证明仍严格校验。前端仅在 sessionStorage 保存当前文档最近运行 ID 与随编辑映射的选区位置，刷新后过滤已处理建议，校验选区仍属于对应目标块。旧任务没有块哈希时沿用整篇快照校验。没有执行中的本地任务且记录未终结时返回 `interrupted`；不自动重跑或断点续跑。
- `payload.traces` 保存 Supervisor／Worker／模型／工具的父子调用标识、耗时、模型、用量、错误码、重试次数、提示词版本及工具 schema 摘要；不记录提示词、工具正文或凭证。原工具审计接口保持兼容。运行／反馈记录使用原有审计存储；数据库故障降级为进程内结果并标记 `audit_store=memory`，此时重启不能恢复。
- 模型限流与 502／503／504、已识别的临时网络错误最多重试一次，等待受取消与阶段截止时间控制，两次尝试分别计费和追踪。权限失效、资料版本变化、预算不足不交给模型修复；工具参数／结果协议仍最多修复一次。不自动重放工具或写入。

## 第一阶段独立 Worker 运行器

现有直接执行、分步执行共用 `AgentRuntimeService.runWorker()` 与 `DocumentAgentToolsService`。第一阶段提取独立运行器，后续已接入下节的基础 Supervisor 决策循环。`read` 步骤映射 Reader，`search` 映射 Researcher，compose、计划和最终汇总沿用 Primary；不改写用户已确认的合法计划。

每次调用拥有独立消息、引用、证据片段和读取证明。下游只接收成功依赖采用的引用及实际证据；同批步骤互不可见。不同查询的压缩片段分别保留，原文不被压缩结果覆盖。修改正文的 Primary 必须自己读取目标区域／精确选区，Reader 的读取证明不继承。

步骤通过 `finish_answer.handoff` 交接结构化资料：`findings` 中每条事实绑定 `evidence_ids`，`missing` 列出缺失信息，`conflicts` 列出待核实矛盾及证据。三个数组均必填，最多分别 6／6／3 项；不接受全空交付。服务端要求引用同时出现在本步骤实际观察内容及最终采用的 `citation_ids` 中，再计算 `complete / partial / insufficient / conflicted`。这验证来源可追溯，不证明模型结论在语义上一定正确。

Supervisor 接收完整且有长度限制的 handoff，不再从截断回答摘要猜测缺口。下游通过 `dependency_handoffs` 与实际 `dependency_evidence` 一起接收；执行成功不等于资料充分，缺口和矛盾需要补查、澄清或在最终回答中明确保留。中间 compose 步骤仍用 `dispatch` 派发，只有 `can_compose=true` 才能进入根最终汇总。审计仅保存覆盖状态与三类条目数量，交接正文不写入未重新校验来源权限的元数据接口。根回答及前端结果协议保持兼容。

工具需同时满足注册、根授权、模式和角色白名单。Reader 不能检索或提交候选；Researcher 只在已选知识范围及联网授权内研究。自定义 MCP 的 `tools_include` 只控制注册；需要向 Researcher 下放的搜索／抓取工具还必须在该服务配置的 `tools_research` 数组中明确列出工具名。内置安全 Fetch 已标记为研究工具，仍受根联网开关约束；未知用途工具不会自动授予 Researcher。

任务共用根取消信号、全局预算和单调递增的 SSE 序号，子任务事件增加可选 `task_id`／`agent_role`。子任务审计标识由服务端任务 ID 加本地轮数组成，供应商调用 ID 只用于本任务对话。任务角色、状态、用量存入既有运行表 payload。根流程只发布一次最终结果、终态并保存一次会话记忆；失败步骤不进入后续批次和汇总，不自动重跑整个步骤或部分成功交付。

自动化与真实服务验收分开记录：[第一阶段验收记录](../../docs/agent-runtime-phase1-acceptance.md)。真实模型脚本从项目根目录执行 `node docs/agent-runtime-real-smoke.cjs`，只创建并检索新生成的合成资料，随后删除；不读取现有知识文档。它会产生正常的运行审计和测试会话，并调用已配置的真实模型、索引及检索服务。人工在界面采纳候选仍需单独验收，脚本不会替用户采纳。

## 第二阶段基础 Supervisor

现有 `plan_execute` 请求由 `AgentSupervisorService` 使用 `plan` 模型决定下一步，支持 `dispatch`、`supplement`、`compose`、`clarify`。服务端校验依赖与状态；必要步骤全部成功才能汇总。补查仅一次，依赖已成功步骤并继承根权限，累计仍最多五步；合法多 compose 计划保持串行执行。直接执行及 Plan 等待确认不变。

主管和 Worker 共享全局执行轮数，研究阶段预留三轮用于下一次主管决策及最终 Primary 读取／提交；主管协议修复最多一次。主管通过根 step 事件展示状态，决策轨迹与用量保存于原运行记录的 `payload.supervisor`。旧前端可直接展示进度，无新增开关或接口。现有 Reflection 保持兼容，独立 Writer／Reviewer 与强制二次审校尚未接入。

调度还为当前批次之外的每个必要步骤预留一次调度、一次读取和一次交接，并预留尚未使用的一次主管协议修复，将当前可用轮数均分给同批 Worker，单步仍最多四轮。Worker 在获分配的最后一轮由模型请求的 `tool_choice` 明确指定 `finish_answer`，提交已有事实与缺口；不足以启动下一批时明确失败，不提高总预算或跳过原计划。可选补查若会占用必要步骤和最终交付额度，在决策校验时拒绝，并将剩余补查额度置为零。该预留不保证所有问题都能在默认预算内查全，最终仍需保留未解决事项。

本轮先实现和自动化回归，再逐项验收真实模型、RAG 与界面采纳：[主管调度验收记录](../../docs/agent-supervisor-phase2-acceptance.md)。

## 工程化验证与对照评测

新增 `agent-execution.spec.ts`、`agent-recovery.e2e.spec.ts` 验证并发预算、未知用量扣账、分类重试、取消、存储恢复、快照冲突、权限撤销及来源版本变化。编辑器事务测试覆盖原选区恢复与错误选区拒绝。

`npm run validate:agents` 检查固定五组合成题集及事实的原文绑定；`npm run eval:agents` 对同一问题分别执行直接运行与已确认多步骤计划，调用真实模型，检查事实是否在同行引用对应的已采用原文、是否越过资料范围、是否保留缺口／冲突及是否编造金额，并记录耗时、P95 和 Token。新增条件／例外保留及含中间 compose 步骤的依赖汇总题。任一检查失败返回非零退出码。评测强制所有数据库、记忆和向量存储使用隔离内存数据，禁用 MCP 与后台 Wiki 编译，只向模型发送新建合成资料，输出工作区 `docs/agent-evaluation.json`。这些确定性检查不能代替完整语义支持率及人工采纳评测，也不代表真实 MySQL／Qdrant／语义向量质量验收。

`npm run test:agent-gates` 运行交接协议、证据越权、预算、主管调度、补查交接、取消、恢复、Wiki 失效及派生纠错回归；使用受控模型和内存存储，不需要真实模型凭证。后端 `.github/workflows/agent-regression.yml` 在 push／PR 执行类型检查、构建、题集校验及这组回归。CI 不自动调用付费模型；真实模型评测单独运行。

配置：`AGENT_MAX_TOTAL_TOKENS`、`AGENT_MAX_MODEL_REQUESTS`、`AGENT_FINALIZATION_TOKENS`、`AGENT_MAX_CONCURRENT_RUNS`。本阶段不引入分布式队列，不提供运行中步骤恢复；多实例部署前需共享执行名额与任务所有权。结构化交接仅存在于当前请求中，完整持久化执行检查点仍属于后续工作。

2026-10-22 的三题历史指标见 [首批验收](../../docs/agent-engineering-acceptance.md)。2026-10-24 扩为五题并增加事实原文绑定检查，最终多步骤 5/5、直接执行 4/5；直接执行的条件／例外题耗尽轮数，整体评测非零退出。前几轮暴露并修正搜索工具未开放、主管中间 compose 歧义、后续步骤预算及最后一轮继续检索，失败报告均保留；其中还出现过缺失信息说明未引用对应原文。最新多步骤五题通过不代表所有场景稳定，详见 [结构化交接验收](../../docs/agent-handoff-acceptance.md)。

## 个人 LLM Wiki + RAG

已完成且全部引用来自可追溯知识文档的稳定知识回答，在返回后自动进入后台整理、独立来源审核及索引，无需用户确认，前端不展示 Wiki 入口。既有 `search_knowledge_base` 优先使用当前范围内有效整理知识，并返回原始证据；无有效命中或明确 `original_only=true` 时使用原始 RAG。Reader 工具权限保持不变。完全相同的回答与来源指纹跳过沉淀；相同来源片段也可能包含新事实，不再仅凭来源坐标判重，新回答继续经过编译及独立质量审核。跨问法判重与主题补充见本节末尾的新增行为及验收边界。

Wiki 继承所有贡献来源的权限、版本及片段哈希；检索前后和最终回答前复核，失效条目隐藏内容。新增 `/ai/wiki` 候选、列表、读取、确认发布及移除接口，普通文档检索不返回 Wiki 层。没有全库自动整理或后台自动覆盖。

首次部署需先备份数据库，再执行 `npm run db:migrate:wiki` 的专用增量迁移，然后构建并启动 API。本地已完成该迁移，本轮自动沉淀不需要新迁移。后台结果单独记录于 `agent_runs.payload.wiki_capture`；失败不影响已完成的回答。当前队列位于进程内，重启不续跑。自动化、界面、真实 MySQL 和真实模型验收分开记录，见 [后台自动沉淀验收记录](../../docs/wiki-auto-capture-acceptance.md)。

后续完善：新候选还需通过可复用性、完整性和实质信息三个质量判断；命中 Wiki 后独立检查用户问题覆盖度，部分覆盖、无关或检查不可用时在同一工具执行内查原始 RAG。审核用量计入根/任务统计，覆盖结果写入工具审计。已完成回答可通过现有反馈接口提交 `helpful/incorrect`；有误反馈取消生成中的沉淀并撤回该回答产生或直接使用的 Wiki，原始资料保留，主回答终态不变。当前本地模型为 `qwen3.7-flash-2026-07-15`，详细边界与复验见 [质量与自动补检记录](../../docs/wiki-quality-acceptance.md)。

Wiki 查询异常（包括命中后失效）同样在本次工具调用中回退原文，Wiki 查询与覆盖检查合计最多 15 秒，为原有 30 秒工具期限保留原文检索时间。取消不会启动回退，迟到 Wiki 结果不提交为证据；原文检索失败仍按工具失败处理。任务审计 `wiki_fallback` 保存 `unavailable/timeout/context_budget`，不保存供应商原始诊断。修复验收见 [Wiki 兜底与沉淀判重](../../docs/wiki-fixes-acceptance.md)。

范围与派生纠错：生成前记录已选知识范围的授权元数据指纹，检索、编译、发布与根最终输出复核；新增资料或范围变化使旧 Wiki 回退原文，初始指纹不可用则跳过 Wiki 与沉淀。新页保存实际使用的 Wiki 祖先版本，错误反馈和主动移除沿对应版本撤回派生页；独立原文整理页保留。无快照旧页停止复用，不上线重编全库。这里仅检测变化，不自动解决所有事实冲突；边界和新一轮结果见 [范围变化与派生纠错验收](../../docs/wiki-evolution-acceptance.md)。

语义判重与补充：在同一有效资料范围内选择一篇相关 Wiki，由原有编译/审核两个请求分别判断 duplicate / supplement / independent / conflict。确认语义重复且来源已包含时记录 semantic_duplicate，不再建页；兼容补充由模型整理新增内容，服务端保留旧正文及重新绑定的引用并追加增量，合并后再审核和检查长度，不截断旧知识。生成的新页通过 topic_id / supersedes 连接不可变主题版本，检索优先采用有效补充页。冲突不覆盖旧正文，两次确认后停止旧知识直接复用；字段原子更新防止反馈清除冲突标记。仍受来源/上下文预算及进程内任务限制，详见 [语义判重与补充验收](../../docs/wiki-consolidation-acceptance.md)。

联合覆盖与缺失补检：前台检索直接按用户和空间从 Wiki 索引召回，再批量读取候选元数据、核验来源与有效后继版本，不再受管理列表最近 100 条的限制；后台精确判重也单独按哈希查询。候选按 Wiki 页去重，最多返回三篇且受共同 token 预算约束，覆盖审核一次判断这些页的联合内容。审计保留 `wiki_ids/query/coverage/missing/reason`，同义改写、仅问已有知识的子集及检索词额外提及的内容不应被误判为缺失。`partial` 时在原查询中补充缺失项检索原文，并返回 Wiki 与原文；未检得的内容仍标为缺失，不宣称已经补齐。不可用、无关、超预算或补检期间 Wiki 失效时只返回原文。返回前及根最终输出继续复核所有采用的 Wiki；引用按来源坐标重绑定，跨历史回答同名标识不串证据。完整记录见 [检索与联合覆盖验收](../../docs/wiki-retrieval-acceptance.md)。
